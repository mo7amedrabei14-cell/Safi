# Plan P0.02 — Account registration, login, and email verification

## Guardrails

- Work directly on `main`; create no task branch.
- P0.01 schema is the starting point. Do not add duplicate account/token tables.
- Keep API-key authentication and existing session routes working.
- Do not connect the local data-cleaning app to the account system (P0.03), and do not change device/session policy (P0.04).
- Do not touch a live database or deploy the service.

## Implementation sequence

1. **Confirm the data contract**
   - Recheck P0.01 migration, workspace/membership constraints, RLS, and the existing session repository.
   - Define P0.02 route request/response shapes and error codes.
2. **Secure account primitives**
   - Add an account repository/service with PostgreSQL and in-memory test implementations.
   - Use audited Argon2id for password hashing/verification and OS-backed random bytes for email tokens.
   - Normalize email; validate bounded input; store only the 32-byte token hash.
3. **Transactional registration**
   - Create user, Argon2id credential, personal workspace, owner membership, Free subscription, and verification token in one transaction.
   - Set `app.user_id` locally before credential table access to respect forced RLS.
   - Make duplicate registration return an enumeration-safe response.
4. **Email verification delivery**
   - Add an SMTP STARTTLS sender configured only by environment variables.
   - Send a link after committing the database transaction; never hold a DB transaction open while sending email.
   - Implement atomic verification and resend-token replacement. A delivery failure leaves the account unverified and allows a new resend attempt.
5. **Password sign-in**
   - Verify with Argon2id; reject unverified/deleted users and invalid passwords.
   - Issue a session through the existing session repository without changing API-key routes.
6. **Routes, errors, and tests**
   - Add register, login, verify, and resend handlers under `/v1/auth`.
   - Add canonical auth error codes and regenerate generated catalogs.
   - Add unit/in-memory and Axum route tests; extend disposable PostgreSQL 18.6 coverage for account provisioning and RLS.
7. **Verification and handoff**
   - Run formatting, clippy, type checks, all tests, build, security checks, and full `make check` through CI.
   - Resolve every task-related failure; do not hide unrelated pre-existing failures.
   - Write `docs/reports/P0.02.md` with exact CI evidence, setup requirements, limitations, and changed files.
   - Stop after the P0.02 report and wait for owner acceptance.

## Dependencies and operational configuration

- Pin every added Rust dependency to an exact version and update the committed `Cargo.lock`.
- SMTP host, port, username, password, sender address, and public verification base URL must be runtime configuration. No value or secret is committed.
- Tests use a fake in-memory mail sender; CI must not require real SMTP credentials.

## Completion is not claimed until

- All acceptance criteria in `docs/tasks/P0.02.md` are verified.
- `make check` passes on Ubuntu and Windows.
- Existing API-key/session compatibility tests pass.
- The final report exists and P0.03 has not started.
