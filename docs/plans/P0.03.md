# خطة تنفيذ P0.03 — ربط تطبيق SafiData بهوية الموقع

## حدود التنفيذ
العمل على `main` مباشرة. هذه المهمة توصل تطبيق سطح المكتب بخدمة الهوية الموجودة في P0.02 فقط. لا يتم تطبيق P0.04 أو P0.05 ولا مزامنة بيانات الملفات.

## خطوات التنفيذ

### 1. عميل API مشترك
- إضافة اختيار عنوان API واحد واضح بحسب بيئة التشغيل.
- إبقاء الموقع على المسار النسبي `/v1/auth`، بما في ذلك Vite proxy.
- في حزمة Tauri المثبّتة، استخدام `SAFI_API_BASE_URL` وقت البناء.
- عند غياب الإعداد في تطبيق مثبت، الفشل برسالة إعداد واضحة بدل محاولة الاتصال بأصل Tauri المحلي.
- عدم تغيير `credentials: omit` أو `cache: no-store` أو `referrerPolicy: no-referrer` أو `redirect: error`.

### 2. أصل API وCSP في سطح المكتب
- إضافة دالة مستقلة لاختبار صحة أصل HTTPS وتطبيعه، مع اختبارات للحالات الصحيحة والمرفوضة.
- تمرير الأصل الموثق إلى Tauri build configuration ليضاف وحده إلى `connect-src`.
- إبقاء بقية سياسة CSP الأصلية كما هي، وعدم فتح `https:` أو نطاقات عامة.
- اشتراط `SAFI_API_BASE_URL` عند إنشاء حزمة Release؛ عدم اشتراطه في فحوص compile المحلية التي لا تنشئ حزمة.
- حقن الأصل نفسه في واجهة Vite المضمّنة حتى يتطابق عنوان الطلب مع ما تسمح به CSP.

### 3. CORS في الخادم
- إضافة middleware صغير داخل `sf-server` دون مكتبة شبكة جديدة.
- قبول أصول Tauri المعروفة وVite localhost فقط.
- التعامل مع preflight قبل الوصول إلى router، والسماح فقط بـ GET/POST/DELETE وOPTIONS والرؤوس Accept/Authorization/Content-Type.
- إعادة `Access-Control-Allow-Origin` للأصل المحدد نفسه، مع `Vary: Origin`، دون wildcard أو credentials.
- اختبار الأصل الموثوق، والأصل الغريب، والطريقة والرؤوس غير المسموح بها، والطلب الفعلي.

### 4. تجربة الحساب في التطبيق
- توصيل شاشة الحساب الحالية بالمسار الجديد من خلال عميل المصادقة نفسه.
- إبقاء نفس تدفق التسجيل/التحقق/الدخول/الخروج الذي ينفذه الموقع.
- إظهار خطأ إعداد API مميز عند غياب أصل الخدمة من النسخة المثبّتة.
- عدم تخزين الجلسة بعد إغلاق الصفحة أو التطبيق.

### 5. التوثيق والقبول
- توثيق متغير `SAFI_API_BASE_URL` في دليل تشغيل سطح المكتب ومتطلبات الخادم.
- إضافة اختبارات العميل وCORS والتحقق من أصل API.
- تحديث CI ليبني واجهة Tauri التجريبية مع أصل HTTPS اختباري محجوز `.invalid`، دون إرسال أي طلب إليه.
- تشغيل بوابات المشروع ذات الصلة وCI على Ubuntu وWindows، ثم كتابة تقرير P0.03 والتوقف.

## المخاطر والقيود المعروفة
- لا يوجد حتى الآن عنوان API إنتاجي مؤكد ضمن إعدادات المستودع؛ لذلك سيكون الاتصال الإنتاجي قابلًا للتهيئة وليس منشورًا أو مثبتًا على نطاق مخمّن.
- الخادم يجب أن يكون متاحًا عبر HTTPS، وأن تُهيأ أمامه طبقة TLS/reverse proxy في النشر الفعلي.
- CORS ليس بديلًا عن المصادقة أو التحقق من الصلاحيات؛ دوره هنا السماح لواجهة Tauri الموثوقة بقراءة استجابات API فقط.
- لا تُعتبر المهمة مكتملة بمجرد أن ينجح TypeScript؛ يجب أن تنجح اختبارات CORS وCSP أيضًا.
