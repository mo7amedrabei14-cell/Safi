# خطة P0.3 — دورة حياة الاشتراك (تجديد / إلغاء / تغيير خطة)

## النطاق

خدمات الخادم فقط، فوق جدولَي `subscriptions` و`subscription_events` الموجودين في 0003 و0005. لا تغيير على مخطط قاعدة البيانات ولا واجهات HTTP (تُؤجَّل إلى 0.6 حسب خطة P0.1).

## القواعد

1. كل عملية تتطلب `OwnerGrant` من `authorize_owner_grant`، ولا تُقبل أي معرّفات Workspace من خارج الخدمة دون تحقق مالك.
2. كل عملية تُنفَّذ في معاملة واحدة: تحديث `subscriptions` + إدراج حدث في `subscription_events` + مزامنة `workspaces.plan_code`. أي فشل يتراجع كاملًا.
3. لا تُقبل خطة غير موجودة أو غير `active` (الخطط المدفوعة تبقى `draft` حتى تفعيل الدفع).
4. التجديد يحسب الفترة من `max(now, current_period_end)` ويضيف شهرًا أو سنة تقويمية بتوقيت UTC، ويُلغي الإلغاء المؤجَّل.
5. الإلغاء المؤجَّل يبقي الحالة `active` ويضع `cancel_at_period_end = true`، والإلغاء الفوري ينقلها إلى `canceled` ويحرّر الفهرس الفريد.
6. الخطة المجانية (`billing_interval = none`) لا تُجدَّد ولا تُلغى؛ تغيير الخطة منها وإليها مسموح.
7. الأحداث تحمل `actor_role = 'owner'` و`from_status`/`to_status`، و`metadata.at_period_end` عند الإلغاء.

## معايير القبول

- اختبارات وحدة لكل رفض وللحالات الثلاث وحدود الأشهر (31 يناير، سنة كبيسة).
- اختبار PostgreSQL حقيقي يثبت الذرّية والأحداث وRLS تحت دور `NOBYPASSRLS`.
- `cargo clippy -D warnings` و`cargo fmt --check` يمران.

## خارج النطاق

- إنشاء اشتراك جديد بعد الإلغاء الفوري (يحتاج تدفق دفع في مرحلة لاحقة).
- استرداد الأموال وتمديد التجربة (لهما حدثان معرَّفان لكن لا خدمة بعد).
- واجهات HTTP وواجهة المالك (0.6/12).
