# خطة تنفيذ المهمة T4.02 — ترحيلات PostgreSQL 18 ومصادقة مفاتيح API وجلسات Valkey عالية الأداء (القسم 9.2، 9.3)

- **معرّف المهمة**: `T4.02`
- **الشريحة**: S4 — الخلفية والحسابات والدفع (القسم 19.10)
- **الفرع**: `task/T4.02`
- **المصادر المقروءة**: `AGENTS.md`، `docs/tasks/T4.02.md`، `docs/spec/09-backend-owner-console.md` (9.1–9.3)، `docs/spec/19-handoff.md` (19.5)، `docs/spec/15-logging.md`، `docs/spec/18-review.md`

## 1. النطاق والقرار المعماري

مخرجات `T4.02` الرسمية هي ترحيلات PostgreSQL 18 الأصلية (بدالة `uuidv7()`، وRLS، وتقسيم `pg_partman`، وPgBouncer، وصفر Supabase). وتنص المواصفة 9.2 على أن جدولي `api_keys` و`sessions` من صميم مخطط S4، وتنص 9.3 على أن كل نقطة تفحص الملكية والصلاحية مع اختبار يثبت رفض الوصول غير المصرَّح. لذلك تُنفَّذ المهمة على طبقتين متكاملتين:

1. **طبقة البيانات**: ترحيلات SQL صاعدة وهابطة للمخطط الأساسي `users`، `workspaces`، `memberships`، `api_keys`، `sessions`، `audit_log` مع RLS وتقسيم `audit_log`.
2. **طبقة المصادقة**: مفاتيح API مخزَّنة مجزَّأة فقط (`hash`)، وجلسات عالية الأداء عبر Valkey 8 بنمط cache-aside، مع فحص نطاقات الصلاحيات وربطها بموجّه Axum 0.8.

لا تُضاف مكتبات خارجية غير مبرَّرة؛ تُستخدم فقط: `sqlx 0.8.6` (متوافق مع القفل المعماري)، `redis 0.32.7` (عميل Valkey)، `blake3 1.5.5`، `async-trait 0.1.92`، إضافة إلى `axum/tokio/serde/serde_json/uuid` الموجودة. كل الإصدارات مثبَّتة بـ `=`.

## 2. مخطط قاعدة البيانات (ترحيل `0001_s4_core`)

- `users`: معرّف `uuidv7()`، بريد فريد، اسم عرض، طوابع زمنية، حذف ناعم.
- `workspaces`: معرّف `uuidv7()`، اسم، خطة، حذف ناعم.
- `memberships`: مفتاح مركَّب (مساحة، مستخدم)، دور محدَّد بـ `CHECK`، RLS.
- `api_keys`: بادئة بحث فريدة، `secret_hash BYTEA` (بصمة BLAKE3 فقط)، نطاقات `TEXT[]`، انتهاء وإبطال، وعمود مولَّد افتراضيًا (`is_active VIRTUAL`) وفق PostgreSQL 18، RLS.
- `sessions`: بصمة الرمز فريدة، الجهاز، النطاقات، الانتهاء وآخر نشاط، RLS.
- `audit_log`: مُقسَّم بالمدى شهريًا على `created_at`، مع تسجيل `pg_partman` عند توفر الامتداد فقط (دون كسر الترحيل على قاعدة بلا الامتداد)، RLS.
- سياسة RLS موحَّدة: `workspace_id = current_setting('app.workspace_id', true)::uuid`، وتُفعَّل `FORCE ROW LEVEL SECURITY` على جداول المساحات.
- الترحيل الهابط يحذف كل الجداول والدوال التي أنشأها الصاعد بترتيب عكسي، بلا حذف امتدادات النظام.

## 3. طبقة المصادقة

### 3.1 مفاتيح API
- الصيغة: `sfk_live_<key_prefix>_<secret>`؛ `key_prefix` من 16 خانة ست عشرية للبحث المفهرس، و`secret` من 64 خانة ست عشرية (وليدة `Uuid::new_v4` مرتين، مولّد عشوائي آمن).
- التخزين: `BLAKE3(secret)` فقط؛ لا يُسجَّل المفتاح ولا بصمته في أي سجل.
- التحقق: بحث بالبادئة من الكاش ثم من قاعدة البيانات، مقارنة ثابتة الزمن (`blake3` + مقارنة على البايتات)، فحص الإبطال والانتهاء، ثم فحص النطاق المطلوب.
- نطاقات: `read`، `write`، `admin`؛ تُترجم إلى `Scope` وتُفحص لكل مسار.

### 3.2 الجلسات عبر Valkey
- إنشاء جلسة بعد التحقق من مفتاح API: رمز `sfs_<64 hex>`، تُخزَّن بصمته في PostgreSQL، وتُكتب نسخة JSON في Valkey بمفتاح `safi:auth:session:<hash>` وTTL متجدد (30 دقيقة افتراضيًا).
- المسار الساخن يقرأ من Valkey فقط؛ وعند الغياب (cache miss) يُقرأ من PostgreSQL ويُعاد ملء الكاش.
- الإبطال يحذف المفتاح من Valkey فورًا ثم يعلّم الصف في PostgreSQL، فلا تبقى جلسة صالحة في الكاش.
- مفاتيح API تُكاش أيضًا (`safi:auth:apikey:<prefix>`, TTL 5 دقائق) لتقليل ضغط القاعدة، مع إبطال الكاش عند الإبطال.

### 3.3 الواجهات
| المسار | الطريقة | الحماية | الوظيفة |
| --- | --- | --- | --- |
| `/health` | GET | عام | صحة الخدمة والإصدار |
| `/v1/auth/whoami` | GET | مفتاح API أو جلسة | هوية الطالب ومساحته ونطاقاته |
| `/v1/auth/sessions` | POST | مفتاح API | إنشاء جلسة لجهاز |
| `/v1/auth/sessions/current` | GET | جلسة | بيانات الجلسة الحالية |
| `/v1/auth/sessions/current` | DELETE | جلسة | إبطال الجلسة الحالية |

- كل رد يحمل `X-Request-ID`، والأخطاء بصيغة `problem+json` برمز من `errors.toml`.
- رموز جديدة: `SF-AUTH-002` (جلسة منتهية)، `SF-AUTH-003` (جلسة أو مفتاح مُبطَل)، `SF-AUTH-004` (صلاحية غير كافية)، `SF-AUTH-005` (خلفية المصادقة غير متاحة).

## 5. الاختبارات ومعايير القبول

1. **مفاتيح API**: توليد/تحليل، رفض سر مُحرَّف، رفض مفتاح منتهٍ، رفض مفتاح مُبطَل، رفض نطاق غير كافٍ، وعدم ظهور السر في التمثيل النصي (`Debug`).
2. **الجلسات**: إنشاء ثم مصادقة، انتهاء، إبطال فوري، وإثبات أن القراءة الساخنة تخدم من الكاش دون لمس القاعدة (عدّاد نداءات المستودع).
3. **الموجّه**: `401` بلا بيانات، `200` بمفتاح صالح، دورة جلسة كاملة (إنشاء/قراءة/إبطال ثم `401`)، ووجود `X-Request-ID` في كل رد.
4. **الترحيلات**: فاحص ثابت يتحقق من أزواج up/down، وحذف الهابط لكل جدول، وتفعيل RLS على كل جدول مساحة، واستخدام `uuidv7()`، وغياب `SERIAL` وSupabase. التشغيل الحقيقي الصاعد/الهابط واختبار العزل بين مساحتين عبر `tools/test-migrations.sh` عند توفر `SF_TEST_DATABASE_URL`.
5. **البوابة**: `make check` أخضر، ثم تحديث `CHANGELOG.md` وكتابة التقرير العربي، والتوقف قبل `T4.03`.

## 6. المخاطر

- لا يوجد PostgreSQL أو Valkey محليًا في بيئة التنفيذ؛ لذلك تُختبر منطقية المصادقة بالكامل عبر تنفيذات ذاكرية للمستودع والكاش، ويُوثَّق أن اختبار الترحيل الحقيقي لم يُشغَّل محليًا. لا يُعلَن نجاح ما لم يُقَس.
- `pg_partman` امتداد اختياري؛ الترحيل يتعامل مع غيابه دون فشل، ويُسجَّل ذلك في التقرير.
