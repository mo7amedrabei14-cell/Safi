## 1. Delivered functionality

P0.02 adds the email/password account lifecycle while retaining the existing API-key and session authentication paths.

- **Registration:** validates normalized email, display name, and password; hashes passwords with Argon2id; and provisions the user, personal workspace, owner membership, active Free subscription, password credential, and one-time verification token in a single PostgreSQL transaction. Duplicate email addresses receive the same outward accepted response.
- **Email verification:** creates 32-byte cryptographically random tokens, stores only their BLAKE3 hashes, and consumes valid tokens atomically. Expired, malformed, unknown, and replayed tokens share the dedicated `SF-AUTH-007` response.
- **Resend:** replaces the previous pending token and keeps the outward response independent of whether the email exists or is already verified.
- **Password sign-in:** verifies Argon2id credentials, rejects unverified/deleted accounts, and issues the existing `sfs_*` session through the existing session service and repository.
- **Sign-out:** revokes the current session through the existing `DELETE /v1/auth/sessions/current` endpoint.
- **Errors:** invalid account request fields use `SF-AUTH-006`; invalid verification links use `SF-AUTH-007`. Auth errors return `application/problem+json` with the request ID middleware retained.

### Public API contract

| Method | Route | Success |
| --- | --- | --- |
| POST | `/v1/auth/register` | `202 Accepted` with an enumeration-safe message |
| POST | `/v1/auth/email/verify` | `200 OK` |
| POST | `/v1/auth/email/verification/resend` | `202 Accepted` with an enumeration-safe message |
| POST | `/v1/auth/login` | `201 Created` with the existing session token and descriptor |

## 2. Security and data handling

- Passwords are never stored or logged in raw form. Password hashes use Argon2id.
- Verification tokens are random, single-use capabilities. Only their 32-byte BLAKE3 hashes are stored in PostgreSQL.
- New verification links use the URL fragment form `/#verify_email=...`. Browsers do not send fragments in the initial HTTP request, avoiding exposure of the token in ordinary query-string access logs. The web app removes the token from the address bar after reading it. Legacy query-string links are still accepted during the transition.
- Registration and account lookup use the existing forced RLS policies plus transaction-local configuration. A SELECT-only trusted authentication lookup policy was added; it does not grant write access.
- Account/session tests exercise the non-owner, `NOBYPASSRLS` application role `safi_p0_01_app`.
- The website keeps the returned session token in React application memory only. It does not write the token to localStorage or cookies. A browser refresh therefore requires the user to sign in again.
- The frontend sends session credentials only in the `Authorization: Bearer` header and uses same-origin `/v1/auth` requests.

## 3. PostgreSQL integration evidence

Added `crates/sf-server/tests/account_postgres.rs`, an explicit PostgreSQL-backed SQLx integration test. It runs in the disposable PostgreSQL 18.6 migration job after migrations and the restricted application role have been prepared.

The test verifies:

1. A deliberately rejected final subscription insert rolls the entire account-registration transaction back; no user/workspace residue remains and no verification email is dispatched.
2. A successful registration creates the user, Argon2id credential, personal workspace, owner membership, one pending token hash, and active Free subscription.
3. An unverified user cannot sign in.
4. Duplicate registration does not dispatch another email.
5. Resend invalidates the earlier token; the new token verifies successfully.
6. A verified user receives an `sfs_*` session which the existing session authenticator accepts.

The migration job reports **1 PostgreSQL account integration test passed**, then confirms migration constraints, RLS behavior, and reverse-order rollback. The test is marked ignored in the generic Rust test suite because it requires `SF_TEST_DATABASE_URL`; `tools/test-migrations.sh` invokes it explicitly in the PostgreSQL job using `--ignored`. This is deliberate test isolation, not an unexecuted acceptance test.

## 5. Runtime setup

The new runnable Axum host is `crates/sf-server/src/main.rs`.

Start the backend after applying the repository migrations to a PostgreSQL 18 database:

```powershell
cargo run -p sf-server
```

Run the web frontend separately:

```powershell
pnpm --filter @safi/web dev
```

The Vite development server proxies same-origin `/v1/*` requests to `http://127.0.0.1:8080`.

| Environment variable | Required | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | Yes | PostgreSQL connection string |
| `SAFI_BIND_ADDRESS` | No | HTTP bind address; defaults to `127.0.0.1:8080` |
| `SAFI_VALKEY_URL` | No | Valkey URL; process-local cache is used if omitted |
| `SAFI_SMTP_HOST` | Yes | SMTP relay hostname |
| `SAFI_SMTP_PORT` | No | SMTP STARTTLS port; defaults to `587` |
| `SAFI_SMTP_USERNAME` | Yes | SMTP username |
| `SAFI_SMTP_PASSWORD` | Yes | SMTP password |
| `SAFI_SMTP_FROM` | Yes | Verified sender mailbox |
| `SAFI_PUBLIC_BASE_URL` | Yes | Public HTTPS origin used to create verification links |

SMTP credentials and database connection strings must be injected at runtime through an appropriate secret/configuration mechanism. They must not be placed in source control, frontend variables, or build arguments.

## 6. Explicit limitations and boundaries

- **No production deployment was performed.**
- **No live or production database was migrated.** The PostgreSQL proof uses a disposable CI PostgreSQL 18.6 instance.
- **No SMTP account was created and no real SMTP credentials were supplied.** CI exercises email dispatch with a capture/fake sender. Actual delivery requires the runtime SMTP variables above.
- A production hosting/reverse-proxy configuration must route same-origin `/v1/*` traffic to the backend. That deployment configuration is not part of this task.
- The session is intentionally memory-only in the website. Persistence/desktop app session coordination is not included here.
