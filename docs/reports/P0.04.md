## ما تم تنفيذه

1. **هوية تثبيت محلية ثابتة**
   - تُنشأ UUID عشوائية عند أول استخدام وتُحفظ في IndexedDB.
   - يعاد استخدام الهوية نفسها في تسجيلات الدخول التالية من ملف المتصفح/التثبيت نفسه.
   - لا يوجد fallback إلى `localStorage` أو إنشاء معرّف جديد في كل تسجيل دخول.
   - إذا تعذر الوصول إلى IndexedDB أو توليد UUID آمنة، يتوقف تسجيل الدخول برسالة مفهومة بدل تجاوز قيد الجهاز.

2. **عقد تسجيل الدخول**
   - يرسل مسارا تسجيل الدخول في `AuthModal` و`AccountAccessSheet` الحقلين `installation_id` و`platform`.
   - الخادم يقبل المنصات المحددة فقط: `windows`, `linux`, `macos`, `web`.
   - يُشتق BLAKE3 بنطاق خاص لكل مستخدم من UUID التثبيت ومعرّف المستخدم؛ لا يُخزَّن UUID الخام.
   - تنسيق Debug لطلب الدخول يحجب البريد وكلمة المرور ومعرّف التثبيت.
   - تسجيل الدخول يرفض الحساب غير الموثق أو المحذوف أو الموقوف.

3. **ربط الجهاز بالجلسة**
   - Migration `0006_session_device_binding` تضيف `sessions.device_id` ومفتاحًا خارجيًا يضمن تطابق مالك الجهاز مع مالك الجلسة.
   - معاملة PostgreSQL تقفل عمليات تسجيل الدخول للمستخدم، ثم تحدث/تنشئ سجل الجهاز، وتبطل الجهاز والجلسة السابقين، وتضيف الجلسة الجديدة. جميع هذه الخطوات تنجح أو تتراجع معًا.
   - تسجيل الدخول المتكرر من التثبيت نفسه يعيد استخدام سجل الجهاز. تسجيل الدخول من تثبيت مختلف يستبدل الجهاز والجلسة السابقين.
   - مصادقة الجلسة تتحقق من حالة الجهاز والحساب من PostgreSQL؛ لا تعتمد على صلاحية الرمز أو مدة صلاحيته وحدهما.

4. **الترحيل والتراجع**
   - Migration 0006 تحفظ سجلًا عكسيًا للحالات النشطة القديمة وتبطلها عند الترقية، حتى يعيد المستخدم تسجيل الدخول بهوية تثبيت ثابتة.
   - ملف `down.sql` يعيد فقط السجلات القديمة التي لم تتغير بعد الترقية، ولا يحيي جلسة قديمة فوق جلسة أحدث.
   - أضيف اختبار لحالة تسجيل دخول في نفس ثانية الترحيل لتجنب خطأ دقة الطوابع الزمنية.
   - لم يُشغَّل هذا الترحيل على قاعدة الإنتاج.

## أدلة الاختبار — CI

| البوابة | النتيجة |
|---|---|
| Full Gate على Ubuntu | ناجحة |
| Full Gate على Windows | ناجحة |
| PostgreSQL 18.6 — تطبيق migrations، قيود المخطط، RLS، rollback واختبارات الحسابات | ناجحة |
| Chromium — اختبار الانترو وهوية IndexedDB بين صفحتين | ناجحة |
| بناء واجهة الويب وغلاف Tauri على Windows | ناجح |
| تنسيق المستودع | ناجح |

اختبار PostgreSQL الفعلي يغطي ربط الجلسة بسجل الجهاز، تخزين البصمة بدل UUID الخام، إعادة استخدام الجهاز نفسه، الاستبدال من جهاز آخر، إبطال الرمز السابق، التراجع الكامل عند فشل إدراج الجلسة، تسجيل دخولين متزامنين، ورفض الحساب الموقوف.

اختبار Chromium يفتح صفحتين منفصلتين ويتأكد من ثبات UUID المخزنة في IndexedDB، ومن عدم استعمال `localStorage` لتخزين معرّف التثبيت.

## الحدود والقيود المتبقية

- معرّف التثبيت **ليس** إثبات هوية عتاديًا أو WebAuthn أو Passkey. هو معرّف محلي يمكن نسخه يدويًا؛ لا يثبت أن الجهاز ماديًا هو الجهاز الأصلي.
- حذف بيانات الموقع/IndexedDB أو استخدام ملف متصفح جديد يؤدي إلى هوية تثبيت جديدة، وبالتالي يعاملها النظام كجهاز آخر ويستبدل الجلسة النشطة.
- اختبار Chromium يثبت سلوك IndexedDB في متصفح حقيقي، وبناء Tauri يثبت نجاح التجميع؛ لم يُنفَّذ تسجيل دخول فعلي من نسخة مثبتة إلى خدمة إنتاجية.
- تقرير P0.03 ما زال يذكر أن `SAFI_API_BASE_URL` مضبوط في الاختبارات على `https://api.safidata.invalid`، ولا يوجد عنوان API إنتاجي حقيقي معتمد. لذلك يلزم تحديد عنوان الخدمة وإعداده قبل إصدار Tauri يستطيع تسجيل الدخول إلى خدمة فعلية.
- رمز الجلسة يبقى في ذاكرة التطبيق فقط؛ لا يُحفظ في IndexedDB أو `localStorage` أو cookies.
- API Key sessions ما زالت مدعومة، ولا ندعي أنها تثبيتات حساب مرتبطة بجهاز.
