## 11. الجودة والاختبار والمراقبة

لا ميزة تُعتبر منتهية قبل أن يثبتها اختبار آلي يعمل في CI، وأي فشل يمنع الدمج والإصدار.

### 11.1 هرم الاختبار

| النوع | الأداة | ما يغطيه | البوابة | 
| ----- | ----- | ----- | ----- | 
| وحدات المحرك | `cargo test` | كل دالة في الأقسام 4.2 إلى 4.11 | تغطية $90\%$ فأكثر للمحرك | 
| اختبارات الخصائص | `proptest` + `codeburn` | تنضيف الناتج مرة ثانية لا يغيّره، والتراجع يعيد الأصل تمامًا، والوصفة حتمية | لا فشل على ملايين الحالات العشوائية | 
| المجموعة الذهبية | ملفات ونتائج متوقعة | $200$ ملف فأكثر ($300+$ مع `No-Cost AI`): عربي متلخبط، هجري، أرقام هندية، ترميزات قديمة، خلايا مدمجة، ملفات ضخمة | أي تغيير في الناتج يحتاج مراجعة وموافقة صريحة | 
| Fuzzing | `cargo-fuzz` | كل المحللات (`xlsx` و`csv` و`json` و`Parquet` و`PDF`) | $24$ ساعة بلا انهيار لكل إصدار | 
| وحدات الواجهة | Vitest وTesting Library | المكوّنات والمنطق | تغطية $80\%$ فأكثر | 
| لقطات بصرية | Storybook مع لقطات آلية | كل مكوّن في فاتح وداكن وRTL وLTR | لا فرق غير مقصود | 
| سيناريوهات كاملة (E2E) | Playwright للويب، `tauri-driver` للديسكتوب | القصص الخمس عشرة في القسم 2 على كل المنصات | كلها خضراء | 
| الإتاحة | `axe-core` + اختبار يدوي بقارئ شاشة (NVDA وOrca) | WCAG 2.2 AA | صفر مخالفات حرجة | 
| الأداء | `criterion` وLighthouse CI | ملفات $10$ آلاف و$100$ ألف ومليون صف، الذاكرة، زمن بدء التشغيل، ميزانيات القسم 6.8 | فشل إن تراجع الأداء أكثر من $10\%$ | 
| الترجمة | فحص آلي | مفتاح ناقص، نص أطول $40\%$، أعطال RTL | صفر نتائج | 
| الترقية | اختبار ترحيل | الترقية من الإصدار السابق ببيانات حقيقية والتراجع عنها | بلا فقد بيانات | 
| المتانة | حقن أعطال | قطع الشبكة أثناء المزامنة، وإنهاء العملية أثناء التصدير | لا ملف تالف أبدًا | 
| الأمان | القسم 8.10 + `Strix` + `Cloudflare Sec Skill` | SAST وDAST و`fuzz` واختراق آلي ومستقل | كل النتائج الحرجة والعالية مغلقة | 

**الكتابة الآمنة للملفات:** كل تصدير يُكتب في ملف مؤقت ثم `fsync` ثم إعادة تسمية ذرية، فلا يبقى ملف نصف مكتوب إن انقطعت الكهرباء.

### 11.2 تعريف «تم» لكل ميزة

1. الكود مكتوب، بلا `TODO` ولا بيانات وهمية.

2. اختبار آلي يغطي معيار القبول في القسم 5.

3. اجتازت الإتاحة والأداء واللقطات والترجمة.

4. التوثيق محدّث (مركز المساعدة والواجهة البرمجية).

5. قرار معماري مسجَّل في `DECISIONS.md` إن وُجد.

6. فحوص الأمان الآلية ناجحة.

7. سطر في `CHANGELOG.md` بالعربية البسيطة.

### 11.3 خط CI/CD

* **تنسيق وفحص:** `rustfmt` و`clippy` بلا تحذيرات، و`eslint` و`prettier`، وفحص الأنواع.

* **الاختبارات:** وحدات ثم خصائص ثم واجهة.

* **البناء** على ويندوز ولينكس (وماك لاحقًا) بنفس السكربت.

* **E2E** واللقطات والإتاحة والأداء.

* **فحوص الأمان** وتوليد SBOM وتوقيع المخرجات بـ Sigstore.

* **نشر كمسودة،** ثم نشر تدريجي (`canary` ثم $10\%$ ثم $50\%$ ثم $100\%$) بتراجع آلي عند ارتفاع الأعطال.

* **سياسات الفرع:** الفرع الرئيسي محمي، وكل تغيير عبر طلب دمج، والالتزامات موقّعة، والإصدارات بترقيم دلالي (SemVer).

### 11.4 المراقبة بعد الإطلاق

* **مؤشرات المنتج (بموافقة المستخدم فقط):** نسبة نجاح كل عملية، الزمن حتى أول ملف نظيف، الخطوات التي يرفضها المستخدمون كثيرًا (تدل على قواعد خاطئة)، ومعدل الأعطال لكل إصدار.

* **أهداف:** معدل جلسات بلا أعطال $99.5\%$ فأكثر.

* **أسبوعيًا:** مراجعة المؤشرات وقائمة الأخطاء الأعلى تكرارًا وطلبات الدعم، وتحويلها إلى مهام مرتّبة.
