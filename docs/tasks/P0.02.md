# Task P0.02 — Registration, password sign-in, and email verification

## Objective

Implement the server-side account lifecycle requested after P0.01: a user can register with an email address and password, verify ownership of that email, and sign in. The existing API-key authentication and session endpoints must continue to work unchanged.

P0.01 already provides `users.email_verified_at`, Argon2id password-hash storage, one-time email-verification token storage, password-reset token storage, a Free plan, and workspace subscriptions. This task must use those structures rather than duplicate them.

## Deliverables

1. **Registration**
   - Add a public registration endpoint under `/v1/auth`.
   - Normalize email addresses consistently (trim and lowercase) and validate email/display-name/password inputs before writing.
   - Hash passwords with the audited Argon2id implementation. Never persist, return, or log raw passwords.
   - Create the user, password credential, personal workspace, owner membership, active Free subscription, and one-time verification token in one PostgreSQL transaction.
   - Do not create an authenticated session until the email is verified.
   - Return an account-enumeration-safe response for both new and already-registered addresses.

2. **Email verification**
   - Generate a cryptographically random, single-use verification token with a bounded expiry.
   - Store only a one-way 32-byte token hash in `email_verification_tokens`; never store or log the raw token.
   - Send the verification link through a configurable SMTP STARTTLS transport. SMTP credentials and the public verification URL come only from runtime environment configuration, never from source control.
   - Add verification and resend-verification endpoints. Re-sending replaces the pending token instead of creating multiple pending tokens.
   - Verification must be atomic, expire correctly, and reject replayed, unknown, or expired tokens.

3. **Password sign-in**
   - Add a public email/password sign-in endpoint.
   - Verify passwords using Argon2id and reject unverified or deleted accounts.
   - Use non-enumerating responses for unknown email addresses and incorrect passwords.
   - On successful sign-in, issue the existing `sfs_*` session through the existing session repository. Keep existing API-key/session routes compatible.
   - Do not add device-transfer or device-limit behavior; later roadmap work owns that policy.

4. **Error handling and security**
   - Add canonical `SF-AUTH-*` error codes and regenerate all derived error catalogs.
   - Keep responses in the existing `problem+json` format with the request ID.
   - Validate request sizes and input lengths; never echo secrets or credentials.
   - Apply account and verification operations in transactions; use prepared SQL only.
   - Keep user credentials behind the existing forced RLS policy by setting `app.user_id` transaction-locally for credential access.
   - Preserve existing API-key authentication, the current session routes, and the single-active-session database invariant.

5. **Automated verification**
   - Add service tests and real Axum route tests for registration, duplicate registration, password validation, wrong password, unverified login, successful verified login, verification expiry, one-time use/replay rejection, resend replacement, and SMTP failure handling.
   - Add PostgreSQL 18.6 migration and real SQLx integration coverage for transactional account provisioning, workspace ownership, Free subscription creation, password verification, token replacement, session issuance, and credential/session RLS. The integration test runs as the restricted `safi_p0_01_app` role in `crates/sf-server/tests/account_postgres.rs`.
   - Prove existing API-key/session tests remain green.
   - Do not run migrations against a live or production database.

## API contract

The route contract is:

| Method | Route | Request JSON | Success response |
| --- | --- | --- | --- |
| POST | `/v1/auth/register` | `{"email":"user@example.com","display_name":"Display Name","password":"12+ character password"}` | `202` with a generic verification-dispatch message |
| POST | `/v1/auth/email/verify` | `{"token":"64-character hex token"}` | `200` with verified status |
| POST | `/v1/auth/email/verification/resend` | `{"email":"user@example.com"}` | `202` with a generic message whether or not the address exists |
| POST | `/v1/auth/login` | `{"email":"user@example.com","password":"...","device_name":"Browser"}` | `201` with `token` (`sfs_*`) and the existing `session` descriptor |

Login tokens are sent only in the JSON response over HTTPS and are consumed by
the existing `Authorization: Bearer sfs_...` session middleware. The public
session routes remain unchanged. Email verification is required before login;
verification tokens are not accepted as authentication credentials.

Invalid login credentials (including unknown, deleted, and unverified accounts)
share the `SF-AUTH-001` response. Malformed account inputs use `SF-AUTH-006`.
Malformed, unknown, expired, and replayed verification links use the dedicated
`SF-AUTH-007` response with HTTP 422. Neither error includes submitted values
or reveals whether an account exists.

## Explicitly out of scope

- Connecting the local data-cleaning application to website identity/session state (P0.03).
- Changing or extending the one-device / one-active-session enforcement policy (P0.04).
- Password reset and account recovery (separate task).
- Passkeys, OAuth/Google/Microsoft, MFA/TOTP, team invitations, billing activation, and payment-provider webhooks.
- Enabling paid plans or changing the approved Free plan.
- Production deployment, production database migration, SMTP account creation, or publishing secrets.
- Storing authentication tokens in browser local storage or changing local-first data handling.

## Acceptance criteria

- A new registration creates exactly one user, one credential hash, one personal workspace, one owner membership, one current Free subscription, and one pending verification token; all are committed or none are.
- The user cannot sign in until the email is verified.
- A valid verification token succeeds once and only once; expired, unknown, and replayed tokens fail safely.
- A successful verified login issues a session accepted by the existing current-session endpoint.
- Wrong passwords and nonexistent addresses do not disclose whether an account exists.
- Duplicate registration and verification resend do not expose account existence.
- SMTP failure never marks an email as verified and never loses the ability to request a fresh verification email.
- No raw password, verification token, SMTP credential, or email body is persisted in logs.
- Existing API-key/session behavior remains compatible.
- Full `make check` and the GitHub Actions gate pass on Ubuntu and Windows.

## Runtime wiring and SMTP configuration

The runnable HTTP host is `crates/sf-server/src/main.rs`. It creates the
PostgreSQL pool, existing API-key/session repositories, authentication service,
SMTP sender, and account service before exposing the Axum routes. Start it with
`cargo run -p sf-server` after applying the P0.01/P0.02 migrations. It binds to
`127.0.0.1:8080` by default. The Vite development server proxies `/v1/*` to
that listener, so the browser continues to use same-origin API requests.

Required runtime environment:

| Variable | Required | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | Yes | PostgreSQL connection string with permissions for the P0.01/P0.02 schema and RLS policies |
| `SAFI_BIND_ADDRESS` | No | HTTP bind address; defaults to `127.0.0.1:8080` |
| `SAFI_VALKEY_URL` | No | Valkey URL; the process-local cache is used when omitted |
| `SAFI_SMTP_HOST` | Yes | SMTP relay hostname |
| `SAFI_SMTP_PORT` | No | SMTP STARTTLS port; defaults to `587` |
| `SAFI_SMTP_USERNAME` | Yes | SMTP authentication username |
| `SAFI_SMTP_PASSWORD` | Yes | SMTP authentication password |
| `SAFI_SMTP_FROM` | Yes | Verified sender mailbox |
| `SAFI_PUBLIC_BASE_URL` | Yes | Public HTTPS website origin used to form `/#verify_email=...` |

Do not put these values in source control, frontend variables, Docker build
arguments, or committed workflow files. Inject them at runtime through the
deployment secret manager. SMTP delivery is attempted only after the account
transaction commits; a delivery failure is recorded as a generic server event
without logging the email address, message body, link, token, or provider reply.
The verification token is carried in the URL fragment rather than the query string, so browsers do not send it in the initial HTTP request or ordinary access-log query fields. The web app also removes the fragment immediately after reading it. Legacy query-string verification links remain accepted during the transition.

The website's production reverse proxy must route same-origin `/v1/*` requests
to this server; deployment configuration remains outside this task. The
registration and resend routes intentionally retain their generic
`202 Accepted` response on delivery failure to avoid account enumeration.

Migration `0004_auth_lookup_rls` adds SELECT-only, transaction-scoped lookup
policies. Existing write policies remain in place. The API must set
`app.auth_lookup` only inside short-lived database transactions; it must not
accept this marker from request headers or request bodies.
